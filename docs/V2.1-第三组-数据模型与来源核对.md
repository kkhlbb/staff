## 2. 数据库版本与项目 schema 是两回事

- IndexedDB 版本：5 → **6**，新增 `migrationBackups`（keyPath `id`，索引 `projectId`）。
  升级逻辑仍只创建缺失 store/index，不重建、不清空。
- 项目 JSON / 项目记录 `schemaVersion`：1 → **2**。
- 任何模块都通过 `storage/db.ts` 的同一个打开器访问数据库，没有第二个来源库。

## 3. 关系确认：从可写布尔改为派生

持久化字段（`Project`）：

```ts
relationRevision: number            // 单调递增，影响关系的操作 +1
relationReview: {
  relationRevision: number          // 确认时的修订号
  fingerprint: string               // 环身份+代号+数值+方向的稳定指纹
  confirmedAt: string
} | null
```

判定（`src/workspace/relation.ts`）：

- 指纹包含 `id / symbol / nominalQ / lowerDeviationQ / upperDeviationQ / sign`，
  排序后计算，排除名称、备注、目标与行顺序；算法为 **FNV-1a 64 位**，
  仅用于一致性判断，不是密码学签名或工程批准。
- `isRelationConfirmed` 要求：凭据存在 + 修订号一致 + 指纹一致。
- 改目标 / 名称 / 备注 / 顺序不递增 `relationRevision`，确认保留。
- 改数值 / 方向 / 代号、增删环递增，改回原值也不恢复。
- 草稿非法时也立即按草稿修订号判定失效，界面显示“待确认（预览）”。
- 工作台、项目列表、打印报告都调用同一个判定函数。

## 4. 本地 V1 项目升级

- 读取路径（`getProject` / `listProjects`）发现 `schemaVersion: 1` 时，在**一个
  readwrite 事务**中：
  1. 把原始 V1 记录写入 `migrationBackups`（完整原始对象，不是升级后字段）；
  2. 写入迁移后的 v2 项目（`termRevision=1`、`relationRevision=1`、
     `relationReview=null`、`migration={fromSchemaVersion,migratedAt,backupId}`）；
  3. 迁移同一项目的草稿（保留无效输入，删除旧 `relationConfirmed`）；
  4. 写 `schema_migrated_v1_to_v2` 事件。
- 任一步失败 → `transaction.abort()`，所有项目保持 V1，不产生半成品；
  下一次读取会重试。
  **自动化（fake-indexeddb）覆盖**：两条 V1 项目中第二条非法时，第一条的项目改写、
  备份与事件全部回滚；备份表/事件表计数为 0；修正后重试一次迁完两条。
  未在真实浏览器制造“事务中途失败”，不把这条记为浏览器已验证。
- 迁移前可先用项目列表的“迁移前影响”面板查看环数/基线/草稿/将清除的确认，
  并导出未改写的原始 V1 项目与草稿到本机文件；恢复=重新导入为新项目（新 ID），
  保留数值/基线/无效草稿输入，不覆盖现有项目、不降级数据库。见
  `evidence-v21-b3/migration-*.png` 与 `迁移前原始备份-2026-11-08.json`。
- 界面在迁移后显示明确提示：旧人工确认无版本凭据、已清除、需要重新确认；
  项目、基线与无效草稿均保留。
- 首次升级策略已由用户在 2026-11-08 批准（保留原始备份与全部输入、明确提示、
  清除旧确认并重新确认）。

## 5. 外部导入分派

| 文件版本 | 行为 |
|---|---|
| v1 | 迁移为 v2；补 `termRevision=1`；保留整数 q、项目/基线/草稿；清除人工确认；来源状态“未检查”；ID 冲突由写入层换新 ID，不覆盖已有项目；非法数值整体拒收、零写入。 |
| v2 | 校验工程输入与来源元数据；清除 `relationReview`；保留文档/版本/绑定元数据；`blobKey` 重新生成，避免读到已退役项目的同名 Blob；所有来源 ID 冲突时整体重映射并保持引用一致；附件明确标记不可用。 |
| 其他 | `unknown_schema_version` 拒绝，不改动已有数据。 |

## 6. 来源核对凭据与失效矩阵

`SourceBinding` 增加 `reviewedTermRevision: number | null`、`reviewedAt: string | null`。
状态由 `src/sources/review.ts` 派生（不保存“有效/失效”布尔）：

| 事件 | 关系确认 | 来源数值核对 | 实现 |
|---|---|---|---|
| 改基本尺寸/偏差/方向、增删环 | 失效（relationRevision+1） | 该环失效（termRevision+1），其他环保留 | 已做 |
| 改代号 | 失效 | 保留；写 `term_symbol_changed` 事件记录前后值 | 已做 |
| 改名称/备注/调顺序 | 保留 | 保留 | 已做 |
| 改绑定区域/页码 | 不影响 | 该绑定核对清空，不动数值与其他绑定 | 存储 API + 测试；来源栏“重框”界面已接 |
| 换关联来源 | 不影响 | 该绑定核对清空，`revisionId/documentId` 更新 | 存储 API + 测试；来源栏“换关联来源”界面已接 |
| 改后改回原值 | 不自动恢复（修订号单调） | 不自动恢复（termRevision 单调） | 已做，含刷新与非法中间态 |
| 同文档导入新版 PDF | 不自动迁移 | 旧绑定显示“待版本复核”，区域/页码不动 | 已做（派生 + UI 标签） |
| JSON 导入缺附件 | 确认清空 | 绑定显示“来源附件不可用” | 已做 |

优先级：环不存在 > 待版本复核 > 附件不可用 > 未核对 > 数值已变 > 已核对。

## 7. 导出契约

- V2 JSON 带 `relationRevision` / `relationReview` / `sources`（documents、
  revisions、bindings）。
- `sources.attachmentsIncluded` 恒为 `false`，并有固定 `sources.notice`：
  “数据备份不含来源附件……”。界面点击“导出 JSON”后也显示同样提示。
- JSON 不包含 Blob 字节；完整 `.cunlian.zip` 属 V2.2，未实现、未宣称。
- 保存失败提示里的按钮显示“导出 JSON 备份（不含来源附件）”，并注明只保留
  来源元数据与绑定坐标；顶部导出与它共用同一提示。
- 引导失败时的应急导出先读来源元数据：读得到就带 `sources` 并提示版本数；
  读不到才降级为普通备份，并明确写“不含来源记录、绑定坐标与附件”，
  不再静默输出空 `sources`。

## 8. 未完成 / 只算缓解的部分

- 迁移前影响与原始备份导出已实现（项目列表面板 + 本机 JSON + 恢复入口）；
  但真实浏览器只验证了“V1→v2 正常迁移/恢复”这一条路径，事务中途失败仅在
  `fake-indexeddb` 自动化中覆盖。
- “标记已核对”按钮只记录当前 `termRevision`，没有专门的“数值对照”对话框；
  用途/数值对照仍靠用户看表格与 PDF。属缓解，不是完整审查流程。
- “重框/换关联来源”保存时必须重新框选区域；没有“只改页码/只改备注”的独立
  小表单。改备注仍可通过重新框选同一区域完成，属可用但不够省事的交互。
- `historicalAcceptance`（选择继续用旧版并填理由）未实现，按任务卡归 V2.2。
- 审查中心、AnalysisSnapshot、报告快照、ZIP 备份与恢复未实现；本批没有把它们
  标为通过。
- 关系指纹是非密码学哈希，只用于判断数据是否变过，不承担防篡改。
- DB 升到 6 后，旧前端（请求更低版本）会得到 VersionError；部署回滚不能只回退
  前端，也不能删库降级。真实双标签页跨版本已做（旧 v5 页面 + 新 v6 页面）：
  旧页面在升级后没有持续连接，停留在旧界面；刷新后显示“页面程序版本过旧”。
  Chrome 的 `blocked` 事件派发不稳定，已增加 15 秒兜底提示，见第二组文档 §1.4。
