# ADR-001 · 证据模型：把"来源"从 PDF 提升为出处对象

状态：**已定稿，待实施**
日期：2026-11-12
作者：宁拙吾
基线：`main = 5b2f06c`
前置：用户拍板——客户手里什么都可能（任务书/扫描件/手绘草图/一句话/样品）；无来源项目要能提交；agent 标签等能力完整后再贴。

---

## 1. 问题

```ts
// src/document-extraction/types.ts:88-94
export interface ExtractionSourceIdentity {
  documentId; revisionId; sha256; blobKey; pageCount
}
// src/document-extraction/draft.ts:581-589
planApplication: 先校 revisionId + sha256，不一致 → SOURCE_STALE，整条管线拒绝服务
```

**没有 PDF = 没有来源身份 = 建不了项。** 这不是界面缺入口，是数据模型里没有"出处来自人"这个可能。

## 2. 决策

新增 **`EvidenceRef`** 联合类型，`ExtractionSourceIdentity` 降级为其中一支（`pdf-text`）。

```ts
export type EvidenceRef =
  | PdfTextEvidence      // 现有 ExtractionEvidence，字段一个不动
  | PdfOcrEvidence       // 扫描件 OCR：page + rect + confidence
  | ImageOcrEvidence     // 草绘照片：imageId + sha256 + rect + confidence
  | UserAttestation      // 用户断言：actorId + at + sessionId + turnId + statement

interface UserAttestation {
  readonly kind: 'user-attestation'
  readonly actorId: string        // 本机用户标识（非姓名，不许自由文本）
  readonly at: string             // ISO 时间
  readonly sessionId: string
  readonly turnId: string         // 哪一轮对话
  readonly statement: string      // 用户原话，逐字保留
  readonly fieldPath: string      // 这话是在定哪个字段
}
```

**候选、决定、应用计划、项目文件、图纸、导出物全部携带 `provenance: EvidenceRef[]`。**

## 3. 不变量（谁实现都必须满足）

**I1　唯一闸门不搬家。**
`isEvidenceComplete`（`types.ts:114`）现在就是"数值不得进入候选"的唯一出口，也是 M02 变异目标。
把它改成 `isProvenanceCompleteness(ref)`：**`pdf-text` 分支必须与现有实现逐条等价**——同样的字段检查、同样的矩形包含容差 `1e-6`、同样在缺项时返回 false。
**M02 变异（去掉任一字段检查）必须仍然变红。** 搬家或另写一份 = 两套真相，禁止。

**I2　出处必须能答"凭什么"。**
每个进入项目的数值，`provenance` 至少一条，且能回答"来自哪份文件哪一页哪一段"或"谁在哪一轮说的"。
**空数组 = 非法**，等同现在的 `isEvidenceComplete(null) === false`。

**I3　失效传播按 kind 分开。**
- `pdf-text` / `pdf-ocr`：所属 revision 的 `sha256` 变了 → 该出处 `stale`
- `image-ocr`：图片 `sha256` 变了 → stale
- `user-attestation`：**不会因文件变化而 stale**；只能被**用户显式撤销**，撤销留痕（谁、何时、撤销了哪句）

**I4　出处不可抹。**
界面、项目文件、导出物三处都必须能读到出处清单。**"无外部来源"的项目，导出物必须自带标记**（见 §6）。

**I5　PDF 路径行为零变化。**
同一个文本层 PDF、同一份确认，改前改后：候选数、候选 ID、`evidenceKey`、幂等键、失效传播、提交结果**全部一致**。这一条靠全量回归证明，不靠声明。

## 4. planApplication 改造

```
改前：if (request.source.revisionId !== draft.sourceIdentity.revisionId ||
           request.source.sha256 !== draft.sourceIdentity.sha256) → SOURCE_STALE
      再要求 candidateIds 非空

改后：1) 校验 draft 的出处集合整体有效（没有任何 stale 出处）
      2) 每个候选的 provenance 非空且全部有效（I2 + I3）
      3) 出处是 pdf-* 的，仍要逐条比对 revisionId + sha256（行为等价）
      4) 出处是 user-attestation 的，校验 actorId/sessionId/turnId 与当前会话一致
         —— 跨会话伪造的 attestation 一律拒绝
```

**判据严格度不变**：仍然是同一套 `computeChange` + `computeCandidateRequirementCheck` 重算，提交时主进程仍要复核基准与预览指纹。**变的只是"依据合法性"的定义。**

## 5. 迁移与兼容

- schema 8 → **schema 9**：`provenance` 为加法字段
- 旧项目读出时：`provenance = [由 sourceIdentity 构造的单条 pdf-text]`，**不重算、不改值**
- 旧提取草稿（`extractionDrafts`）不迁移，按既有规则判过期
- `PROJECT_DB_VERSION` 与 `PROJECT_SCHEMA_VERSION` **不是一回事**，改 schema 时按仓库既有约定分开处理

## 6. "无外部来源"的标记（不是装饰）

| 位置 | 必须出现 |
|---|---|
| 项目列表 | 「无外部来源」徽标，与有来源项目视觉可区分 |
| 项目头/图纸标题栏 | 「依据：用户输入，无外部原文件」 |
| DXF / SVG / PDF 导出 | 文件头注释 + 标题栏 + **文件名后缀 `-userinput`** |
| 提交动作 | 勾选「这些尺寸由我提供，无原文件可核对」才能签 |

**理由**：不标记的话，AI 编出来的零件图与甲方任务书建的图导出后完全一样。这是诚信底线，不是 UI 细节。

## 7. 必须新增的能力（供后续任务卡引用）

| 项 | 说明 |
|---|---|
| `createProject` 工具 | 从零建项目，来源为 `user-attestation` 集合 |
| `setChain` 工具 | 写组成环：符号、基本尺寸、上下偏差、增/减环 |
| `setRequirement` 工具 | 写条款区间，**只接受用户明确给出的值**，模型不得代填 |
| `setBinding` 工具 | 参数 ↔ 环绑定 |
| 提交勾选 + attestation 冻结 | 提交时把 attestation 集合随版本冻结 |

## 8. 禁止事项

1. **不许模型填写条款区间**（无来源时此项必须由人给或引用标准库），违反即拒绝工具调用
2. **不许让无来源项目在列表/图纸/导出物上与有来源项目外观一致**
3. **不许绕过 `planApplication` 直接写项目**（会失去同一套门禁）
4. **不许把闸门复制一份**给新来源类型用（I1）
5. **不许静默采信低置信 OCR**：置信度必须显示，且必须人工誊写确认

## 9. 验收判据（实施完成后逐条核）

1. 全量回归绿，且 PDF 路径的候选数/ID/幂等键与改前**完全一致**（I5）
2. **M02 变异仍然红**（I1）
3. 新增变异 **M24**：把 `user-attestation` 视为"总是有效"→ 跨会话伪造用例必须红
4. 无来源项目：建项 → 提交 → 出图 → 导 DXF，四处标记齐全（§6）
5. 出处失效传播：改 PDF 文件 → 该 PDF 出处 stale；其他出处不受影响（I3）
6. schema 9 迁移：schema 8 项目读入写出后，参数与判据不变

## 10. 已决（2026-11-12 用户拍板）

1. **条款区间的来源：只认用户原话。**
   无来源项目里，条款区间必须由用户逐字给出（连同原话一并记录进 `statement`）。
   **不许引用"GB/T 5847 + 等级"之类作为出处**，也不许从标准库推导默认值。
   → 实施后果：`setRequirement` 工具**只接受用户在界面/对话中的显式输入**；模型传值一律视为伪造，返回 `REQUIREMENT_MUST_BE_USER_GIVEN`。

2. **`actorId` 与会话标识：用户第一次打开项目时手工输入。**
   用户要自己掌控身份，不做隐式账号体系。

3. **手绘草图置信阈值：`< 0.9` 一律强制人工誊写**，不提供"自动通过"选项。
   置信度必须在界面上逐条显示，`image-ocr` 出处里带 `confidence`。

4. **`-userinput` 后缀：默认加。**
   导出文件名默认带 `-userinput`；项目内标记不可关。用户可改文件名，但改后界面提示「来源标记仍在项目内，文件名已改」——**不许连标记一起消失**。

## 11. 会话标识：不需要 UUID（修正）

初版我提"系统生成 UUID 保证唯一性"——**这是把服务端的思路搬到了本地单机应用，多余。** 用户的质疑成立。

理由（想清楚后的）：

- **本地开源单机部署，不存在多租户**，两条 attestation 撞到"同一个 sessionId"这件事，现实里只有一个用户在操作，不会发生
- 更根本的：**本地生成的任何 id 都证明不了身份**。UUID 由本机生成，谁都能生成一个；它防不了伪造，只解决"这条记录归哪一次输入"
- 一个 UUID 对用户来说不可读、不可查、不可引用——**成本全是用户的，收益是理论上的**

### 改成：项目内自增序号 + 用户备注名

| 字段 | 谁定 | 说明 |
|---|---|---|
| `actorId` | 用户手输（首次打开项目，存进项目文件） | 责任人自述，用于显示与追溯 |
| `sessionSeq` | **系统自增（1、2、3…）** | 项目内天然唯一，可读、可引用（"第 3 次输入的"） |
| `sessionLabel` | 用户手输（可空） | 备注名，如「2026-11-12 复检」 |

界面上显示 `老王 · #3 · 2026-11-12 复检`。**没有唯一性校验、没有格式校验、没有长串手输。**

### 必须同页写清的一点（防止后面误用）

**`provenance` 不是防伪机制。** 它回答的是"这个值当初是从哪来的"，不回答"这个值是真话吗"。
本机没有任何东西能证明"老王"真是老王。**真正的把关只有两处：用户点确认，以及项目文件本身可读可审。**

将来若做团队版/云端，才需要签名或服务端分配标识。**那是另一件事，不往本地应用里塞。**
