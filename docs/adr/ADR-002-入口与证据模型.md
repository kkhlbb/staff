# 入口与证据模型（对应"最完整情况"）

写于 2026-11-12。用户拍板三条前提：
1. 客户手里**什么都可能**（任务书 / 一句话 / 手绘草图 / 实物样品），按最完整做
2. 无来源项目**要能走到提交**
3. agent 标签等能力完整后再贴

---

## 一、五种入口，一条管线

不要把"意图建件"当成 PDF 之外的第四条岔路。**正解是：把"来源"从 PDF 提升成"出处对象"（EvidenceRef），PDF 只是其中一种。**

| 客户手里有什么 | 入口 | 产出候选的出处类型 |
|---|---|---|
| 规范任务书（文本层 PDF） | 现有 `runExtraction` | `pdf-text`（版本+页+选区+原文） |
| 扫描任务书 | OCR | `pdf-ocr`（页+包围盒+识别置信） |
| 手绘草图 / 手机照片 | 图片 OCR + **人工誊写** | `image-ocr` + `user-attestation` |
| 一句话需求 | 意图建件（对话追问） | `user-attestation` |
| 实物样品 | 用户量录 | `user-attestation` |

**五种入口最后都产出同一形状的东西：候选（值 + 单位 + 出处）。** 再走同一条 `planApplication` → 草稿 → 复核 → 提交 → 出图。

### 现状与目标的差

```
现在：ExtractionSourceIdentity = {documentId, revisionId, sha256, blobKey, pageCount}
      planApplication 第一件事：校 revisionId + sha256（draft.ts:581-589）
      没有 PDF = 没有身份 = 整条管线拒绝服务

目标：provenance: EvidenceRef[]
      EvidenceRef =
        | { kind:'pdf-text', documentId, revisionId, sha256, page, rect, quote }
        | { kind:'pdf-ocr',  documentId, revisionId, sha256, page, rect, confidence }
        | { kind:'image-ocr', imageId, sha256, rect, confidence }
        | { kind:'user-attestation', actorId, at, sessionId, turnId, statement }
      planApplication 的校验从"PDF 哈希一致"改成"**每一处关键值都有合法出处，且出处未失效**"
```

## 二、无来源提交怎么才能不撒谎

**核心一句：证据链的目的不是"必须有 PDF"，而是"任何一个数字都能追到一个人或一份文件"。**

抓住这一条，无来源提交就不是编造：

| 项 | 有任务书 | 无任务书 |
|---|---|---|
| 参数来源 | 任务书第 3 页 | **用户 2026-11-12 在会话 #xxx 说** |
| 公式来源 | 原文公式 | 用户选定（或 GB/T 5847 方法） |
| 条款区间来源 | 原文条款 | **用户明确给出**（不许模型编） |
| 计算正确性 | 内核 q 整数 | **内核 q 整数（完全一样）** |
| 判据严格度 | 门禁重算 | **门禁重算（完全一样）** |
| 提交授权 | 用户点确认 | 用户点确认（多一道"我确认这些值来自我"） |

**变的是"依据来自谁"，不是"检查严不严"。** 这条必须写进架构，否则"无来源"会变成"无检查"。

### 必须做的四件配套（不是装饰）

1. **出处清单进项目文件**：每个值带 `provenance`，提交时冻结
2. **图纸上固定标注**：无来源项目的标题栏写「依据：用户输入，无外部原文件」
3. **导出物带标记**：DXF/SVG/PDF 的文件头或标题栏带上同一条，文件名加后缀（如 `-userinput`）
4. **提交时的一次显式确认**：「这些尺寸由我提供，无原文件可核对」——勾了才签

**理由**：否则一个 AI 编出来的零件图，导出后和甲方任务书建的图长得一模一样。**那是产品诚信问题，不是细节。**

## 三、需要新增的能力（代码层面）

| 项 | 内容 | 依赖 |
|---|---|---|
| `EvidenceRef` 类型 | 四种出处联合类型，替换单一 PDF 身份 | — |
| `provenance` 贯通 | 候选 → 决定 → 计划 → 项目文件 → 图纸 → 导出物 | EvidenceRef |
| 工具 `createProject` | 从零建项目（无 PDF 身份） | EvidenceRef |
| 工具 `setChain` | 写组成环（符号、基本尺寸、上下偏差、增减环） | 同上 |
| 工具 `setRequirement` | 写条款区间（**只能来自用户明确给出**） | 同上 |
| 工具 `setBinding` | 参数 ↔ 环的绑定 | 同上 |
| `planApplication` 泛化 | 来源校验改成"出处完整性校验" | EvidenceRef |
| 未来源状态语义 | 「无外部来源 · 全部用户输入」固定标签 + 提交勾选 | 同上 |

**三条禁止**：
- 不许模型自己填写条款区间（无来源时此项**必须**由人给）
- 不许让"无来源项目"在列表/图纸/导出物上与"有来源项目"外观一致
- 不许走"绕过 planApplication 直接写项目"的捷径（会失去同一套门禁）

## 四、"能力完整"的验收门槛（贴 agent 标签之前必须全过）

用户要求"能完整实现需求后再贴标签"，那就把"完整"定义死，免得之后扯皮：

1. 五种入口都能建项：文本层 PDF / 扫描件 / 图片草图 / 一句话 / 量录
2. 无来源项目能提交、能出图、能导出 DXF，且出处标记全链路可见
3. agent 能处理的参数超过当前 3 个（内径/外径/长度），至少支持组成环级改动
4. 真模型回归进 CI（不再是默认跳过的 14 条）
5. 界面语言全部翻成人话（无 `stage`/`preview` 这类工具名外露）
6. 侧栏能回答「谁在干活、干到哪、卡在哪、依据是什么」

**这 6 条不齐，不许在产品上写"Agent"。**

| # | 内容 | 成本 | 说明 |

| **0** | 设计定稿：EvidenceRef + 无来源提交语义（纯文档，不写码） | 小 | 先把"证据=可追到人或文件"写死 |
| **1** | L1-a 整份失败 → 部分成功 | 小 | 便宜且必要，独立 |

| **3** | 意图建件（4 个新工具 + 用户断言 + 提交勾选） | 中 | 产品的 agent 叙事从这条起 |

| **5** | 扫描件 OCR | 大 | 入口扩容，必须 4 已就位 |

| **8** | L5 STEP（仅回转体） | 大 | — |
| **9** | agent 标签 + 界面语言全翻 | 小 | 等 1–8 的验收门槛过 |

## 六、风险（提前说）

- **第 2 步是最容易做成"两套真相"的地方**：EvidenceRef 一旦并行存在，旧路径必须原样跑通（哈希、幂等、失效传播全部回归），否则等于把 V3.5/V4.0 踩过的坑重踩一遍
- **无来源 + 能导出** 会让"AI 生成的图"流向加工现场。出处标记必须做到**想删都难**（标题栏 + 文件头 + 文件名），不能只靠界面提示
- **手绘草图的 OCR 置信度不可靠**：必须逐条显示置信并要求人工誊写确认，**不许静默采信低置信结果**
